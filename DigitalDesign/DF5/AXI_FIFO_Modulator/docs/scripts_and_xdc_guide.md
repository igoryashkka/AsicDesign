# Гайд: що роблять скрипти і що таке .xdc

Цей файл — для людини, яка вперше відкрила проєкт і не розуміє, навіщо тут `.tcl`/`.bat` файли
і що за дивний файл `constraints/*.xdc`. Стосується не тільки DF5 — та сама схема скриптів
використовується в DF3 і DF4.

## Навіщо взагалі скрипти, а не просто відкрити Vivado і поклацати?

Vivado GUI зберігає проєкт (`.xpr`) як велику купу бінарних/XML файлів у папці `project/`.
Ці файли погано зберігати в git (конфлікти, розмір, нечитабельний diff) і незручно
відтворювати на іншому компʼютері. Тому весь проєкт **генерується наново з нуля** з коротких
текстових Tcl-скриптів: береш чистий репозиторій, запускаєш один `.bat`-файл — і Vivado сам
створює проєкт, підтягує всі `.vhd`/`.xdc` файли, налаштовує властивості. В git зберігаються
тільки самі RTL/constraints/скрипти, а не згенерований проєкт.

## Що таке Tcl і чому Vivado ним керують

Vivado має вбудований Tcl-інтерпретатор. Все, що можна зробити мишкою в GUI, можна виконати
командою в Tcl (`create_project`, `add_files`, `launch_runs`, ...). Файли `*.tcl` у цьому
проєкті — це просто послідовність таких команд, яку Vivado виконує в консольному режимі
(`vivado -mode tcl -source файл.tcl`), без відкриття вікна.

## Хто за що відповідає

```
scripts/
  build.bat        <- точка входу для людини (Windows, cmd)
  settings.tcl      <- єдине місце з налаштуваннями проєкту (назва, part, шляхи)
  build.tcl          <- створює/наповнює Vivado-проєкт (виконується ОДИН раз на початку)
  run.tcl            <- запускає синтез/імплементацію/бітстрім/XSA на вже створеному проєкті
  common/*.tcl        <- маленькі допоміжні функції, якими користуються build.tcl/run.tcl
```

### `settings.tcl`
Центральна конфігурація: назва проєкту (`_xil_proj_name_`), назва top-модуля
(`_inst_top_name_`), part FPGA (`_part_number_`), і шляхи до папок з джерелами/constraints/
симуляцією. Всі інші скрипти спочатку роблять `source settings.tcl`, щоб мати ці змінні.
Тут же підвантажуються (`source`) всі файли з `common/`.

### `common/*.tcl`
Чотири маленькі допоміжні процедури, які повторно використовуються:
- `get_dir_list` — рекурсивно обходить папку і повертає список усіх підпапок (щоб знайти
  вкладені `sources/rtl/якась_підпапка/`).
- `get_file_list` — для списку папок повертає список файлів із потрібними розширеннями
  (`vhd`, `sv`, `xdc`, ...).
- `lflat` — "розплющує" вкладені Tcl-списки в один плаский список.
- `ldelete` — видаляє елемент зі списку за значенням.

Завдяки цьому `build.tcl` не треба вручну перелічувати кожен `.vhd`-файл — досить покласти
файл у `sources/rtl/`, і скрипт сам його підхопить при наступному запуску.

### `build.tcl`
Виконується, коли проєкту ще не існує (або коли `build.bat` викликається без прапорів
синтезу/імплементації). Робить по порядку:
1. Створює Vivado-проєкт (`create_project`) у папці `project/` з обраним part-номером.
2. Виставляє властивості проєкту (VHDL 2008, куди складати IP-кеш, мову симулятора, ...).
3. Скановує `sources/rtl` і додає всі знайдені RTL-файли (`add_files`).
4. Якщо вже є Block Design (`sources/bd/microblaze.bd`) — підвантажує його, валідує,
   генерує wrapper (`make_wrapper`) і виставляє top.
5. Скановує `constraints/` і додає всі `.xdc`.
6. Скановує `sources/simulation` і додає файли симуляції.

Після цього в `project/` зʼявляється повноцінний `.xpr`, який далі можна відкрити руками
в Vivado GUI (наприклад, щоб намалювати Block Design мишкою — це `build.tcl` за вас не
робить, IP Integrator треба збирати в GUI).

### `run.tcl`
Працює з уже створеним проєктом (`project/*.xpr` має існувати). Приймає 4 прапорці
(synth/impl/bit/xsa) і залежно від них запускає:
- `launch_runs synth_1` — синтез;
- `launch_runs impl_1` — імплементацію (place & route);
- `launch_runs impl_1 -to_step write_bitstream` — генерацію бітстріму (`.bit`);
- `write_hw_platform` — експорт апаратної платформи (`.xsa`) для Vitis (софт для MicroBlaze).

Кожен крок перевіряє статус попереднього (наприклад, не дасть згенерувати бітстрім, якщо
імплементація не завершилась успішно).

### `build.bat`
Обгортка для людини: парсить прапорці командного рядка і викликає `vivado` з потрібним
Tcl-скриптом.

| Команда | Що робить |
|---|---|
| `build.bat` | Створює проєкт (`build.tcl`) |
| `build.bat -syn` | Синтез (`run.tcl`) |
| `build.bat -impl -bit` | Імплементація + бітстрім (`run.tcl`) |
| `build.bat -xsa` | Експорт `.xsa` (`run.tcl`) |
| `build.bat -all` | Синтез + імплементація + бітстрім за один прогін |
| `build.bat -cln` | Видаляє папку `project/` |

## Що таке `.xdc`

`XDC` = **Xilinx Design Constraints**. Це текстовий файл (теж на Tcl-синтаксисі), яким ти
кажеш Vivado дві речі, яких немає в самому RTL-коді:

1. **Де фізично на кристалі знаходиться кожен зовнішній сигнал** (на який саме пін
   мікросхеми виведено `clk`, `rst_n`, LED, кнопку тощо) і з яким електричним стандартом
   він працює (3.3V CMOS, диференціальний і т.д.).
2. **Часові обмеження** (timing constraints) — на якій частоті працює вхідний clock, які
   затримки допустимі. (У цьому проєкті переважно перший пункт — timing здебільшого дає
   автоматично `clk_wiz`/MicroBlaze BD.)

Без `.xdc` Vivado синтезує схему у вакуумі: логіка є, а куди вона підключена фізично —
невідомо, бітстрім згенерувати не вдасться (буде помилка "unconstrained ports").

### Як читати рядки .xdc

```tcl
set_property -dict {PACKAGE_PIN W21 IOSTANDARD LVCMOS33 } [get_ports reset_rtl_0]
```

- `get_ports reset_rtl_0` — вибрати порт з іменем `reset_rtl_0` **на верхньому рівні
  проєкту** (це має точно збігатись з назвою зовнішнього порту в top-модулі / Block Design
  wrapper — якщо назви не співпадуть, Vivado просто мовчки проігнорує рядок).
- `PACKAGE_PIN W21` — фізичний контакт мікросхеми (буква+число з даташита/схеми плати),
  куди електрично підведений цей сигнал на друкованій платі.
- `IOSTANDARD LVCMOS33` — електричний стандарт вводу/виводу (тут: 3.3V CMOS). Має
  відповідати тому, що реально розведено на платі — неправильний IOSTANDARD може навіть
  пошкодити мікросхему чи периферію.

Рядки, що починаються з `#`, — закоментовані (нічого не роблять), часто лишені як
довідник/шаблон "ось так виглядає констрейн для цього типу піна, розкоментуй і встав
свій номер піна".

### Що робити з TODO в `constraints/Artix-7-XC735T.xdc`

У цьому проєкті є два закоментовані TODO-рядки:
```tcl
#set_property -dict {PACKAGE_PIN W22 IOSTANDARD LVCMOS33} [get_ports {modulated_out}]
#set_property -dict {PACKAGE_PIN Y22 IOSTANDARD LVCMOS33} [get_ports {axi_rx_led_o}]
```
Це означає: "тут треба вивести `modulated_out` і `axi_rx_led_o` на реальні піни плати,
але я (той, хто писав скелет) не знаю точний номер піна на твоїй платі — подивись
схему/pinout своєї плати, знайди вільний GPIO/LED пін, розкоментуй рядок і встав правильний
`PACKAGE_PIN`". Номери `W22`/`Y22` — не вигадані навмання, вони скопійовані з уже
існуючого `pwm_r_o_0`/`pwm_r_o_1` у DF4 як приклад формату рядка, а не як гарантовано
правильний пін саме під ці нові сигнали — обов'язково звір з документацією плати.
